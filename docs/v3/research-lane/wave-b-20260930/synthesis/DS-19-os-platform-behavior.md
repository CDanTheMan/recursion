## The question

Which observable Windows/Linux contracts must any implementation satisfy on each supported OS profile before a language, store, process library, or terminal library is chosen? The report reframes the blocking seams — process creation and descendant containment, PTY/ConPTY, filesystem atomicity versus durability, signals/console events, clocks, resource limits, service supervision, and crash recovery — as one behavioral envelope to be qualified per pinned platform, not optimized per subsystem.

## Key findings

- **Process creation and containment (SD).** On Windows, Job Objects are the strongest built-in family primitive; a child normally stays in its parent's job chain, and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` terminates associated processes when the last job handle closes. But configured (including silent) breakaway can deliberately let children escape, so "uses a Job Object" is not "descendants cannot escape." `PROC_THREAD_ATTRIBUTE_JOB_LIST` assigns the job at creation instead of relying on a later step. Microsoft says ordinary job messages other than notification-limit messages are not guaranteed, and start/exit messages can be missed if completion-port association races an active job — absence of a notification is not proof no event occurred (SD).
- **Linux containment (SD).** Process groups/sessions/foreground groups remain useful for terminal job control but are not resource containment. `clone3(CLONE_INTO_CGROUP)` places a new process directly into a cgroup v2, closing the "spawn then migrate" accounting window; `cgroup.kill` kills a cgroup and its descendants; `pidfd` signaling avoids the numeric-PID-reuse race. `posix_spawn()` offers only a constrained surface and is itself implemented via clone-like machinery in current glibc. Cgroup membership is administrative state that must be protected against unauthorized migration/delegation (SD/M).
- **Terminal semantics (SD).** A Linux PTY is kernel-mediated: line discipline, canonical vs noncanonical processing, signal-generating characters, software flow control, and `SIGWINCH` on `TIOCSWINSZ` to the foreground process group are explicit interface. ConPTY instead exposes UTF-8 text interleaved with VT sequences and performs console-API/code-page translation internally; the host decodes output and serializes input. `ClosePseudoConsole` sends `CTRL_CLOSE_EVENT`; clients can keep producing output while disconnecting; starting with Windows 11 24H2 build 26100 the call returns immediately to avoid deadlocks, while older builds can wait indefinitely if output is not drained/closed. Final-frame/cursor-query deadlock hazards are also documented. A timeless claim such as "ConPTY close blocks until the tree is gone" is therefore false; transport-close requested, client-disconnect observed, containment state, and execution settlement must be separable facts.
- **Atomicity is not durability (SD).** Linux `rename()` atomically replaces an existing destination from the name-lookup viewpoint; `renameat2(RENAME_NOREPLACE)` can reject an existing target where supported. But `fsync(file)` does not necessarily persist the containing directory entry — a separate directory `fsync()` is required. NFS `rename()` can be reported as failed after the server already performed it before crashing.
- **Windows persistence differs (SD).** `ReplaceFileW`, `MoveFileEx` (with `MOVEFILE_WRITE_THROUGH`), and `FlushFileBuffers` exist, and write-through/unbuffered modes are recommended for critical data, but the cited Win32 contracts give no general POSIX-style "rename then directory-fsync" recipe. `FlushViewOfFile` does not flush metadata or guarantee hardware-cache contents reached media; combine it with `FlushFileBuffers`. Over a network the guarantee is explicitly local-only: data may have left the computer while still in the remote server's cache. The conclusion is that Windows's proof obligation is *different*, not weaker.
- **Locking (SD).** Linux `flock()` is advisory and tied to the open file description, released when the descriptors close including after process teardown; a cooperator can ignore it. Windows `LockFileEx` denies overlapping ordinary reads/writes per mode, but mapped-file access bypasses the byte-range lock, and release after termination/handle close is not guaranteed instantaneous. A persistent "lock file exists" is not a safe liveness oracle on either platform; PID reuse can make stale ownership look current. The inferred target is a kernel lock plus a generation/instance identity and an explicit recovery procedure.
- **Paths (SD).** Microsoft says not to assume case sensitivity, lists reserved characters and device names, and documents the traditional `MAX_PATH` 260 limit plus long-path mechanisms and the Windows 10 1607+ opt-in. The project's own repository has paths long enough to need explicit Windows Git long-path handling.
- **Signals, time, resources (SD/M).** `GenerateConsoleCtrlEvent` cannot confine `CTRL_C_EVENT` to one process group as a POSIX signal-to-group operation can; Windows service control is a separate SCM protocol. Clocks differ: Linux `CLOCK_MONOTONIC` excludes suspended time while `CLOCK_BOOTTIME` includes it; Windows `QueryPerformanceCounter` is for high-resolution intervals, not externally synchronized UTC. So "deadline in five minutes," "lease expires while asleep," and "UTC audit stamp" are different requirements. cgroup v2 `memory.high` throttles/reclaims without OOM while `memory.max` can enter cgroup OOM, with `memory.events` counters (`high`, `max`, `oom`, `oom_kill`, group kills); a Windows Job memory ceiling instead fails the commit and can emit a completion-port notification (SD). A single portable "OOM" status would erase material evidence (M).
- **Supervisors (SD).** systemd defaults `KillMode=control-group` and warns that main-process-only killing can leave processes outside the manager's lifecycle; restart policies and watchdogs can relaunch abnormal exits. The Windows SCM keeps a failure count and performs an indexed recovery action. A Stop/PAUSE guarantee must ensure supervisor recovery cannot silently reinterpret an intentional stop as a crash needing relaunch.
- **Portfolio framing (M).** The report separates five research programs — cross-platform execution conformance; durable filesystem/state semantics; terminal/PTY interoperability; process containment and service supervision; and security/environment portability — and judges cross-platform execution conformance the most generally useful, because the other four become subordinate dimensions of one release question: can a pinned environment execute, contain, observe, stop, recover, and persist work without silently changing the platform's correctness model?
- **Method rule (M).** The test is not whether both systems have a "process group," "kill tree," "flush," "terminal," or "memory limit"; it is what happens under the same negative trace — child escapes, parent dies before registration, PID is reused, the output pipe fills during shutdown, disk fills between write and flush, the machine suspends across a deadline, or a supervisor sees an abnormal exit. The platform passes only if the required observation and recovery oracle still hold.
- **Compatibility layers are separate cases (SD/U).** WSL2 `/mnt/c`, WSL2's Linux filesystem, Git Bash/MSYS2, embedded terminals, SMB, and NFS must not inherit certification from native Windows or native Linux. Microsoft documents DrvFS metadata/permission/case differences and recommends the WSL filesystem for Linux-tool workloads. The conformance matrix marks Native Windows and Native Linux each **Unqualified**, with every non-native row a distinct mandatory case; no cell may turn green by analogy.
- **Crash and recovery (SD/M).** What survives a hard kill, reboot, power loss, and a suspended laptop differs per OS; PID reuse, stale lock files, and half-written state must be detected and reconciled, and an unknown state must not be silently "repaired" without evidence. The report's decisive stop conditions include a surviving owned process accompanying a full-stop claim, a truncated state accepted as canonical, a new process mistaken for an old lock owner, and any restart of intentionally stopped work that performs admitted work.

## Recommendation and falsifier

The report recommends a **contract-first, native-semantics qualification model**: specify one behavior contract but qualify each pinned platform profile through native semantics and preregistered negative traces (descendant escape, parent death before registration, PTY/ConPTY teardown, atomic-replace crash, stale lock/PID reuse, disk full/quota, memory pressure/OOM, supervisor restart race, suspend/resume, network-storage interruption). Each recommendation names a competing option and a decisive falsifier:

1. Contract-first over a lowest-common-denominator abstraction whose API shape becomes the spec; falsified if such an abstraction passes the full corpus with no platform side channels and preserves every native distinction and `unknown` state. No library was selected or evaluated.
2. Kernel containment anchor plus stable process identity over process-group-only tree walking; falsified if tree-walking matches containment/detection across all profiles with less privileged state and no false "fully stopped."
3. Terminal transport non-authoritative over inferring effect completion from EOF/shell exit/final prompt; falsified only if the terminal channel itself becomes an authenticated, durable, replayable effect receipt.
4. Certify persistence per filesystem/storage profile, starting local; falsified for `/mnt/c`/SMB/NFS only when the same crash/power/partition corpus passes on a pinned client/server/mount configuration.
5. Model resource exhaustion as a fault family (throttle, allocation refusal, process kill, group kill, unknown) rather than one status; falsified only if no downstream recovery, accounting, retry, or observability decision depends on the distinction.
6. Subordinate supervisor restart to canonical Stop/PAUSE authority; falsified only if a campaign proves every restarted instance is fenced before it can admit or resume work, including during partial-state recovery.

The three honest outcomes for any profile are **qualified at a pinned configuration, rejected/unsupported, or unknown pending named evidence** — never "probably equivalent to another platform."

## What this does not prove

- No language, store, framework, renderer, process library, PTY library, or multiplexer is selected.
- There are no measured claims; every cell is source-documented, modelled, or unknown.
- No current OS build, kernel, terminal, filesystem, or distribution is certified.
- ConPTY teardown, cgroup/OOM, rename/fsync durability, lock release, and supervisor races are unmeasured on this project's hardware, filesystems, and builds.
- The Linux cgroup/pidfd containment claim is conditional on permissions preventing workload-directed migration and still needs adversarial measurement.
- WSL, compatibility shells, embedded terminals, SMB, and NFS are not qualified and gain nothing by analogy.
- Nothing is implemented, deployed, or written into a protected path.

## Open Owner decisions

- Is WSL2 a supported production platform, a development convenience, or both?
- Is canonical state on SMB/NFS supported, conditionally supported, or explicitly out of scope for the first release?
- Must containment resist intentionally hostile descendants, or only buggy/cooperative tools?
- What is the required definition of "survives power loss": application-consistent state after VM reset, host reset, or physical interruption?
- Does a suspended laptop consume task/lease time? (Linux deliberately offers both suspend-excluding and suspend-including clocks.)
- Which terminal embeddings, beyond native terminals, are first-release qualification targets?
- Is an escaped/unobservable descendant a hard platform failure or an explicit recoverable `unknown`?
