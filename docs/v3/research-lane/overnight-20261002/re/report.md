# R-E: Operator-provisioned trusted launch boundary

Research return • 2 October 2026 UTC • Candidate design, not an accepted implementation

## Decision summary

D-029 is accepted: pursue an operator-provisioned boundary outside Recursion's readable domain. Public documentation supports feasible **conditional** Windows and Linux isolation designs. It does not establish that any Recursion profile currently has that property. Every native profile remains unqualified; every conformance result in this report is **unexecuted**.

Five conclusions determine the design:

1. A different process, clean environment, encrypted credential store, Job Object, cgroup, or opaque identifier is not, alone, a credential confidentiality boundary. The security relationship must deny Recursion both direct access and the ability to enlist a more privileged component to read on its behalf.
2. A separate credential-owning principal with an externally administered launch service is a plausible candidate on every accepted native floor. The operator can instead sandbox all Recursion-controlled code while leaving the already-authenticated tool outside. The second approach may avoid moving authentication, but broad host access, same-user helper services and inherited handles make its evidence burden larger.
3. The secret-bearing CLI is an essential trust dependency. If a prompt, tool call, plugin, executable/configuration change, artifact request or debug command can make that CLI export its secret, denying the parent process a memory read has not established D-029. Arbitrary stdout/JSON is a data channel, not a declassifier.
4. A malicious component that knows a secret and controls an unrestricted output stream can encode that secret. No generic scanner can establish the universal absence of such flows. The honest strong claim is conditional on an explicitly trusted, pinned credential-facing component and enforced separation of untrusted tools, inputs and output-release paths. If that separation is unavailable, use the exact label **non-intermediation-by-policy only**.
5. A synthetic sentinel campaign can demonstrate zero detected credential-material transfers in a specified, completely observed corpus and falsify isolation with one leak. It cannot prove an unrestricted, all-programs, all-time noninterference theorem. This distinction is part of the acceptance oracle, not a reason to abandon D-029.

Recommendations in this report are collected in §R. Each has a competing option, a decisive falsifier and a non-proof. No language, store, framework, sandbox product, runtime, transport encoding or vendor is selected. No route is qualified; authentication, entitlement and counsel clearance remain separate.

## R-E.Q01 — Exact adversary, principals and property

### Principals and trust boundary

**O (operator)** provisions and can revoke the installation. **R** is Recursion and the entire transitive domain it controls: kernel, adapters, plugins, workers, arbitrary subprocesses, updaters it may command, writable binaries/configuration, output renderers, session stores and any helper endpoint available to its credentials. Treat R as compromised, curious or buggy from the first instruction it executes, not just after a convenient initialization step.

**B (boundary)** is an independently provisioned and protected launch/control service. **C** is the authenticated CLI's credential-facing portion. **T** is any tool, plugin, repository code or command C runs; T is untrusted unless specifically audited and included in C's trusted computing base. **V** is the independent synthetic-test observer. B/C/V are never silently reclassified as R just to simplify an implementation, nor silently removed from R merely by giving them a different process name. If a distributed product includes a credential-reading boundary component, public wording must disclose that component and say the orchestrator/tool domain cannot read its credentials; it must not imply that the entire bundled system contains no credential-bearing component.

The baseline trusted computing base contains the OS kernel and applicable security subsystem, operator provisioning, B's executable/configuration and small request decoder, C's credential-facing code, and the explicitly identified output release mechanism. Excluded adversaries: kernel/firmware compromise, hostile administrator/root, physical memory acquisition and a malicious credential-facing C. These exclusions must appear beside the claim. Untrusted tool execution, hostile prompts and project configuration are **not** excluded.

For the selected profile P, let S be all provider credential material in scope: reusable access/refresh tokens, API secrets, cookies, private signing keys and any equivalent authenticator. Let RRead(P,t) be everything R can obtain through permitted OS access or reachable interfaces at time t, including permission changes it can make and induced actions by helpers. It includes data received then deleted. Encrypted credentials that R can decrypt count as readable. A bearer-like launch capability is not the provider credential but is separately sensitive authority.

**Candidate strong property (I):** starting from an operator-validated state with no S in R, the permitted launch/control/workspace interface never gives R credential material or a decrypt/export/injection capability that produces it. B/C keep the material outside RRead for startup, operation, failures, recovery, update and teardown. C may present credentials directly to the intended provider through its own authorized authentication implementation; that is outside R and not a claim that no component uses credentials.

Two obligations must both hold: **direct non-access** (R cannot read or alter the secret domain to gain reads), and **induced-flow non-access** (R cannot direct B/C/T to return it through an allowed channel). Protecting only the first is insufficient. Availability and whether authorized credential use spends quota are different properties.

## R-E.Q02 — Assurance levels and honest claim wording

The following are research labels, not new product tiers or changed Owner decisions:

- **Policy-only:** R promises not to open credential material but possesses effective access or can regain it. Useful for accidental-use avoidance and source-review accountability. Fails the compromised-R threat model.
- **Direct isolation only:** enforced OS separation blocks direct files/store/memory reads. It is a meaningful intermediate result but not the complete D-029 claim when C can return secrets on demand.
- **Conditional strong boundary:** direct isolation plus protected launch inputs, credential-free untrusted tools, and controlled outputs, assuming a trusted pinned B/C and an uncompromised OS/operator. This is the candidate qualification target.
- **Unconditional noninterference against malicious C:** not established and, with arbitrary C-controlled output, impossible as stated. Even a fixed-width status or timing channel may encode bits across requests. A scanner of known raw values cannot prove otherwise.

Recommended external wording after qualification: “In profile P, provider credentials stay in the operator-provisioned authentication boundary. Recursion and its tools cannot read them through the qualified interfaces. This assumes the operating system and the pinned credential-facing boundary remain trusted.” Before qualification: “non-intermediation-by-policy only; strong boundary unqualified.” Never say a sentinel run proves that no conceivable information about credentials can leak.

Structural isolation provides enforcement against an R process that disobeys policy; policy-only supplies no such containment. Neither establishes honest provider behavior, absence of kernel vulnerabilities, absence of physical or microarchitectural side channels, correctness of third-party code, provider revocation, authorization to automate a subscription, or freedom from quota use. Credential confidentiality also does not stop a stolen launch capability from invoking an allowed task. Recommendation R01 addresses this separation.

## R-E.Q03 — Operator provisioning, authorization and revocation

The operator contract (I; R02/R03/R07) is explicit:

1. Choose a supported exact profile and a credential domain already authenticated through the user's own tool. Provision R with a distinct principal or externally enforced sandbox. Provision B independently of R. The user signs in directly inside C's domain if necessary; no token migration, copied auth home, login interception or password handling by Recursion is a setup shortcut.
2. Protect B/C binaries, search paths, libraries, scripts, configuration, auth helpers, credential stores, dumps, update channel and launcher registration against R writes and administrative modification. Audit R's effective groups, privileges, inherited handles/FDs and access to desktop/secret-service/session buses. B must not trust mutable workspace code at its own privilege.
3. Authorize an exact launch profile: CLI identity/version, legal/route admission handled elsewhere, workspace scope, allowed verbs, allowed tools, bounded arguments/environment, artifact release schema, expiry, task/attempt binding, maximum concurrency and current revocation epoch. Installing a boundary confers none of these grants by itself.
4. Provide only a purpose-limited invocation capability. No OS logon token, process-memory handle, shell endpoint, secret-store session or general impersonation handle is given to R. Keep administrative control and runtime use separate.
5. Revoke new admission and renewals at B, advance the authorization epoch, interrupt/drain the selected execution scope and reconcile in-flight outcomes. Operator-side provider logout/revocation is a distinct action; deleting a launch capability does not revoke an already copied provider token.
6. Revalidate after OS patch, CLI/plugin update, principal/ACL/privilege change, workspace exposure, new output field, auth method or recovery. A lost credential machine requires separately authorized local authentication on its successor; continuity capsules carry work and evidence, not credentials.

Under policy-only the operator trusts R itself not to read, modify or emit secrets. Under conditional strong isolation the operator instead trusts the OS, provisioning and B/C to enforce the boundary even if R fails. That reduces one trust dependency but adds a privileged/separately administered component, update/recovery duties and potential availability failures. A user with full administrative power can remove the boundary; R must not inherit that power. Intentional operator disclosure is outside the advertised property and should be recorded as a different mode, not retroactively called protected.

## R-E.Q05 — Windows boundary design candidates

### W-A: Distinct R principal, operator-owned authenticated launcher

The operator retains their already-authenticated CLI under C's identity and starts B independently, or provisions a tightly scoped service to manage that identity. R runs as a different unprivileged principal. Workspaces are explicitly shared at minimum rights; C's auth home, processes and launch dependencies are not. B validates a task capability, selects an allowlisted absolute executable and protected configuration, builds a clean environment, associates containment before work and owns the returned full-access process/thread handles. R receives an application-level launch ID and bounded control/result endpoints, never the OS token or raw process handle. [W01, W02, W08, W14]

Separate controls exist for submit, status, interrupt, drain and scoped artifact release. Neither submit nor resume accepts an arbitrary executable, working directory outside the bound workspace, auth-home override, additional plugin directory, debugging switch, environment map or shell command executed as C. Any arbitrary T execution occurs under a credential-free principal/domain. C must document and demonstrate that its internal tools do not bypass that arrangement. [I]

**Benefits:** understandable SID/ACL separation; preserves existing operator login without token copying; independent stop/revocation even if R crashes. **Costs:** account/session provisioning; workspace permissions; service/launcher update security; operator login availability; more recovery states. **Failure modes:** privileged service accepts arbitrary args/config; returns PROCESS_ALL_ACCESS; grants generic pipe write; trusts mutable hook or binary; launches a tool as C. **Decisive falsifier:** any such path causes R's synthetic hostile request to obtain the sentinel or gain C-equivalent execution. **Non-proof:** no guarantee against malicious C, admin compromise, arbitrary encoded output, or route entitlement. [R04]

### W-B: Operator-launched constrained Recursion, ordinary C outside

An external launcher starts R and every R-controlled process under a configured AppContainer/restricted context before R's first instruction. C stays in its normal authenticated identity; B is outside R's container. Only authorized workspace trees and an authenticated B endpoint are exposed. Even if R is same base user, the effective sandbox must prevent access to unrestricted helper services, secret stores, process memory, desktop capture and ways to run an unrestricted child. It must also protect R-invocable launch registrations from modification. [W04, W10, W16; I composition]

**Benefits:** no new credential principal; R itself is the contained adversary. **Costs:** broad harness tooling, host integrations and filesystem access may require many carefully bounded broker capabilities; all descendants and alternate launch routes must remain confined. **Failure modes:** full-trust escape/helper, capability expansion, excluded process, ambient handle or broad resource grant. **Decisive falsifier:** the probe reaches C's store or induces a same-user unrestricted service to return it despite the verified R token being contained. **Non-proof:** the AppContainer name or packaging format does not prove effective containment; raw C output and malicious C remain unresolved. [R04]

### W-C: Same-user subprocess plus clean environment (comparator)

R starts the user's CLI, does not intentionally read authentication files, masks known log fields and restricts normal tool paths. This has fewer provisioning failures and broader compatibility. It is **policy-only** if R can inspect C's memory/store or change code/configuration to cause export. A clean child environment does not remove the parent's own access. Successful hostile synthetic read/export is the decisive falsifier of any stronger label; normal CLI success is no proof of confidentiality. This comparator is useful as the disabled control, not a replacement decision for D-029. [R04/R08]

**Opaque handles require semantic inspection:** an OS access token, read-capable process/file handle or general RPC credential is not made safe by being opaque. The only acceptable R-side object grants the bounded operation, binds caller/task/attempt/current epoch and is revocable at B. An output pipe can still carry a secret, so W-A/W-B require §Q12's output tests.

## R-E.Q06 — Windows hard limits and unresolved compatibility

- **Creator rights survive a restrictive target DACL.** CreateProcessAsUser documents that the returned process handle remains valid with full access even if the caller could not reopen it. Therefore moving C to another account while R itself launches and retains that handle defeats the intended separation. B must be the creator and never transfer dangerous rights. [W08]
- **Session/desktop assumptions are not portable.** Handle inheritance cannot simply cross Terminal Services sessions. Services run in session 0 and should not expose privileged interactive windows on the user's desktop. A headless credential owner might have no usable user profile, unlocked store or interactive renewal path. Credential/profile loading and no-login recovery are U per CLI. [W08, W11]
- **Integrity and UI restrictions are not substitutes for a trust domain.** Default MIC chiefly protects integrity; UIAccess is expressly designed to cross some process/integrity barriers. R must not gain it, and C must not display credentials on a surface R can inspect. Automated login under R's screen/clipboard control fails the intended setup premise. [W03, W12]
- **Privilege and object-control inventory is mandatory.** SeDebugPrivilege, process duplication/injection access, writable service/launcher configuration, token impersonation and mutable DLL/plugin paths can nullify a nominal SID separation. A helper that returns file bytes or performs arbitrary commands is part of R's effective reachability. [W02, W13, W15; I closure]
- **Pipe ACLs and handle inheritance are sharp edges.** Default security descriptors are not the intended minimum; generic write can admit pipe-instance creation. Endpoint authentication, explicit rights, one-use request binding and closed handle inventories are necessary candidates, not proof from local IPC alone. [W07, W09, W14]
- **No blanket Windows impossibility is established.** The floor includes relevant primitives. What is unknown is whether each exact CLI, update mechanism, tool architecture, desktop requirement and constrained R workflow is compatible. Failure of one design requires narrowing the profile or the policy-only label, not an unsupported claim that a higher edition or another sandbox automatically solves it. [R08]

[6.6](https://docs.kernel.org/6.6/admin-guide/cgroup-v2.html), [6.12](https://docs.kernel.org/6.12/admin-guide/cgroup-v2.html), [clone3](https://man7.org/linux/man-pages/man2/clone.2.html)

**D — exact Landlock floor delta:** the v6.6 UAPI lacks v6.12’s network/scoped fields. The 6.12 guide documents ABI-dependent TCP-port, abstract-socket and signal restrictions, not a destination/application allowlist. The 6.6 guide lacks these later interfaces. [6.6 UAPI](https://raw.githubusercontent.com/torvalds/linux/v6.6/include/uapi/linux/landlock.h), [6.12 UAPI](https://raw.githubusercontent.com/torvalds/linux/v6.12/include/uapi/linux/landlock.h), [6.6 guide](https://docs.kernel.org/6.6/userspace-api/landlock.html), [6.12 guide](https://docs.kernel.org/6.12/userspace-api/landlock.html)

## R-E.Q08 — Linux boundary design candidates

### L-A: Operator-provisioned separate principals and boundary-owned launch

Provision R as an unprivileged UID without C's auth home, groups, keyring possession, session bus, ptrace rights or control over B. B runs in the separately authorized credential identity or a narrowly privileged supervisor that changes identity before C's executable starts. C uses its existing credential store; R never opens, serializes or transports its values. B owns the executable/configuration allowlist, fresh environment, private runtime directory, workdir validation, open-FD inventory, cgroup membership and output release. Untrusted tools execute in a separate credential-free T domain. [L01, L04–L15, L18; I composition]

The R channel can be a pre-provisioned connected local endpoint or authenticated local IPC carrying a scoped application capability. Peer UID alone is not the task authorization. SCM_RIGHTS transfers an FD referring to the same underlying object; it does not diminish what that object permits. Thus B may hand R the result/control endpoint, never a secret-file, C-memory, namespace-entry, session-bus or privileged service FD. Credentials remain C-side. No transport/serialization is selected. [L11]

**Benefits:** well-defined UID/DAC separation, compatibility with ordinary CLI credential persistence, runtime without root when identities and containment are provisioned beforehand. **Costs:** one-time operator administration; workspace group/ACL design; service and login lifecycle; recovery and cgroup delegation; privileged supervisor risk if used. **Failure modes:** supplementary group leakage, writable auth helper, shared keyring/bus, inherited FD, wrong privilege-drop ordering, cgroup escape or same-identity tools. **Decisive falsifier:** hostile R or its T can obtain the sentinel, launch code as C, or regain protected access through B. **Non-proof:** safe against neither host root/kernel compromise nor malicious C; no route compatibility or entitlement established. [R05]

### L-B: Externally constrained rootless R; C remains outside

The operator executes a small external launcher that removes sensitive inherited FDs/environment and enters a constrained R domain before untrusted R code runs. Compose available namespace, filesystem, LSM/Landlock and syscall restrictions so R cannot reach C, its session bus, user-manager execution APIs, raw process interfaces or writable launcher. B/C remain outside this domain and expose only the minimal launch capability. The separate R domain rather than C's container is the key direction. [L01–L03, L05, L15, L20–L21; I]

**Benefits:** a rootless runtime and potentially no separate account/login; preserves operator's auth. **Costs:** complete filesystem/IPC/desktop/helper mediation; compatibility of a useful general harness; inherited-FD audit; different Linux ABIs/policies; independently delegated cgroup subtree for lifecycle control. **Failure modes:** same-UID service acts on R's request outside its sandbox, unrestricted IPC, open host-root FD, insufficient ABI, an unrestricted pre-existing R thread or alternate exec path. **Decisive falsifier:** R reaches the sentinel through any such deputy or re-launches unconstrained R. **Non-proof:** namespacing alone, a “rootless” label or a successful launch gives no strong claim; global microarchitectural side channels and C malice remain excluded. [R05]

### L-C: Containerize only the secret-bearing CLI under the same host user

This is an important losing comparator unless a separately trusted supervisor also constrains R. A parent namespace can see child processes; the creating parent UID has capabilities in its child user namespace. Mount masking inside C limits C's view, not automatically R's access to its host credential files or memory. Add cgroup limits and a clean environment and the direction error remains. [L01–L03]

**Benefit:** familiar packaging and resource control. **Cost:** extra namespace/image policy plus a misleading isolation appearance if unchecked. **Failure:** parent R reads/attaches or asks C to export. **Falsifier of the claimed boundary:** successful parent read despite C's namespace isolation. **Non-proof:** this finding does not say every container configuration is insecure; it rejects that topology as sufficient evidence. A separately constrained R or different principal creates a different candidate. [R05/R08]

**Cross-lane compatibility constraint:** B cannot transparently create a C/T split that an upstream CLI does not expose. If built-in shell/file/plugin execution shares C's credential-capable process or identity, a separate tool principal is only a desired property, not an available wrapping feature. Strong qualification requires exact, documented unmodified-binary invocation/configuration support, or another independently authorized route. This report proposes no vendor-binary patch, authentication shim, token relay or credential proxy to manufacture that support. R-H's route-specific unmodified-binary/authentication restrictions and R-F's invocation evidence are additional admission constraints. Public OS primitives cannot close this compatibility unknown; H-E01 must identify the supported split before H-E04 can qualify it. If no compatible split or equivalent enforced protection exists, retain the policy-only claim ceiling or refuse a task requiring strong isolation.

All candidates strip secrets from **R's** environment and keep C's required auth inputs C-side. “Secret-stripped environment” must not accidentally mean deleting C's only documented authentication mechanism and silently substituting a copied token. The capability grants launch, not general credential use/export, and replay/renewal checks happen at B.

## R-E.Q09 — Linux no-root and local-host limits

A host with ext4 and cgroup v2 has storage/control prerequisites, not automatic authorization to create a distinct identity, change security policy or manage a cgroup. Distinguish **no root at runtime after operator provisioning** (plausible L-A) from **no administrative provisioning ever, unrestricted same-user R** (no demonstrated strong boundary). An externally preconstrained rootless R may be feasible, but only if every required restriction and helper exclusion is available. [I; R05/R08]

- User namespaces may be configured off, capped or restricted by the distribution/LSM. Ubuntu 24.04 documents AppArmor restrictions on namespace capabilities for unconfined unprivileged programs. Do not turn off system protections as an implicit fallback; request explicit operator setup or label/refuse the stronger profile. Debian/RHEL-specific effective settings and updates remain U for this report rather than inferred from the kernel floor. [L16, L17]
- Yama mode 1 is not a protection from a qualifying parent debugger. PR_SET_PTRACER exceptions and namespace capability relationships matter. A denial of `ptrace(PTRACE_ATTACH)` does not prove denial of every read-mode procfs surface; environ and mem use distinct checks. [L01, L05–L08]
- A shared session keyring can survive exec, and possession/user permissions must be audited. Merely choosing an anonymous keyring or avoiding a recognizable label is not proof that R cannot retrieve a key. Secret Service is another trust boundary with its own actual daemon and bus policy. [L04, L09]
- Use the [canonical delegation premises](#linux-cgroup-facts). Effective delegation must be checked before qualifying a rootless supervisor; a working hierarchy is not authorization for R to administer it. [I]
- Mount/PID/user namespaces share the host kernel. Namespace capability denial reduces reach; it does not prove absence of kernel vulnerabilities or all information leaks. Persisted host-root/device/namespace FDs, shared `/proc`, shared mounts, desktop/session buses and IPC sockets can bypass the intended view. [L01–L03, L11, L15]
- Use the [exact Landlock floor delta](#landlock-floor-facts). Runtime ABI/configuration must be interrogated by the future preflight. Best-effort reduction may improve policy-only safety, but cannot silently keep a strong label when a claim-critical restriction disappears. [I]
- Dumps, swap, journal/error paths and backups must be outside R or excluded by an enforced policy. Core dump handling is host configuration; a process that avoids deliberate logging can still leave crash-state material. This report makes no secure physical-erasure claim. [L19]

## R-E.Q11 — Competing option sets and decisive rejection tests

| Option | What it can plausibly buy | Decisive falsifier of the claimed strong boundary | What it does not prove |
|---|---|---|---|
| Separate OS principal | OS-enforced file/process/store distinction | R can read via group/ACL/store, alter launcher/code, inherit dangerous handle or induce C tool export | Different identity alone is not mediation, CLI correctness or entitlement |
| Container/namespace/AppContainer | Constrain the adversary's view and operations | R remains outside and can inspect C, or an allowed helper launches outside containment | Container branding/resource control is not confidentiality |
| Handle-passed opaque launch capability | Avoid exposing provider bytes or a general credential reference resolver | Handle/object permits read/export/impersonation/arbitrary exec, or replay succeeds after revocation | Opacity is not attenuation; a stolen capability can still cause its authorized effect |
| Broker with no shared address space | Separate implementation and grant enforcement from R memory | Same-user R can debug B, modify it, call an overly general endpoint or read its logs | Process separation is not principal separation; broker compromise remains possible |
| Policy-only | Avoid deliberate credential handling; simpler operation | Any allowed hostile read/export succeeds while a strong label is shown | No enforcement against compromised R; scans cannot upgrade it |
| Strong output mediation with credential-free tools | Prevent ordinary data paths returning protected material | Tool reads S, debug/exception/artifact path releases it, or writable config changes auth behavior | No universal defense against a malicious trusted secret-bearing C using arbitrary encodings/timing |

These options compose; they are not mutually exclusive product choices. In particular “broker + opaque token” still needs OS isolation, and “separate principal” still needs tools/output confinement. A candidate is rejected for its stated assurance claim even if ordinary work still completes. A correctly refused unsupported route is not a compatibility success. [R01–R08]

## Boundary lifecycle under D-022

Proposed mapping (I; R07), preserving selected-agent versus owned-tree scope. B is an enforcement endpoint subordinate to current kernel-issued authority; it is not a second canonical writer or executive. Local durable receipts/spools provide evidence, not autonomous grant issuance. The monotonic authority epoch is distinct from IPC delivery/reset cursor epochs.

| Control | Boundary action | Required evidence and remaining uncertainty |
|---|---|---|
| `checkpoint` | Ask C/T to finish the defined checkpoint boundary; persist credential-free task cursor, operation IDs and allowed artifacts; keep auth state C-side | Validated checkpoint identity, output-release cursor and unfinished-effects list. No memory dump of credential-bearing C; checkpoint support U by CLI |
| `interrupt` | Deliver the documented scoped interruption after admission fencing as required by the requested operation | Receipt distinguishes accepted request, delivered control, local process observation and effects unknown. Never equate with rollback |
| `drain` | Close new work/credential-use admissions and renewal; allow only recorded in-flight completion/reconciliation and secret-safe output release until an explicit deadline | Drain allowlist, deadline, pending IDs and terminal/unknown disposition; timeout escalation must already be authorized; no unbounded retry or refresh loop |
| Aggressive Stop | Fence selected-agent dispatch and forcefully interrupt the selected agent without waiting for its operation | Selected process/session termination/control observation; descendants explicitly listed separately. In-flight external effect can remain unknown |
| Full Stop | Fence selected scope and its owned subagents/tools/monitors/supervisors; prevent relaunch; terminate/reconcile all owned work through B | Scope membership, relaunch fence, current native query, output drained/truncated record, effect/accounting settlement or explicit unknown. Do not kill unrelated work in a shared C server |
| Lazy Stop | Close new admission; wait for next declared observable tool/turn/checkpoint boundary; then stop selected scope | Named boundary plus absolute deadline; no observed boundary means waiting/timeout, not invented completion; configured escalation only |

On R disconnect B follows the previously granted bounded policy; socket close neither revokes all grants by magic nor proves a process exited. On B crash/restart, it first reconstructs identity/epoch and reconciles owned processes and unsettled requests before any launch. If it cannot know whether submission happened, it reports `admission_unknown` and refuses duplicate retry until reconciliation or a qualified idempotency mechanism. Revocation invalidates capability use at the receiver; a cached launch success is not a renewable grant. Zero owned processes is distinct from no external effects and from provider-side token revocation.

G-05's version/schema negotiation, snapshot materialization, cursor-incarnation and ACK-release blockers are not solved by this report. A launch endpoint must refuse incompatible control semantics before effects; its event/receipt cursor must bind stream identity/incarnation and current authority context. R-E supplies security obligations to that contract and consumes FU-04 native behavior evidence. It does not freeze a new wire format, choose ACK semantics or invent a store.

## R-E.Q12 — Provider-free conformance design

### Scope and formal limits

All cases below are **specified, unexecuted**. They use only synthetic credentials and local fake CLI/processes on separately authorized disposable targets. No account, login, provider SDK call, credential lookup in a real user's store, external host, network service, model inference or paid operation is involved. Local IPC only; AF_INET/AF_INET6 egress is denied and witnessed. A fake credential-use endpoint is an in-memory/local-IPC deterministic mock, not a provider. The current report creates no prototype or target account.

The universal assertion “zero secret bytes” needs a precise oracle. Ordinary outputs naturally share individual byte values with a secret. The property is **no transfer of credential material or tested recoverable derivatives**, not absence of every octet value present in S. An exact sentinel substring test alone misses encodings, splits, partial disclosure and transient buffers. Static reachability/authority evidence plus adversarial behavioral tests is required. Finite tests can prove the predicates of the tested finite trace; they cannot certify every future program and channel.

### Fixture topology and manifest

V owns a sealed synthetic fixture seed and creates at least two unequal 64-byte high-entropy credential payloads, S0 and S1, inside B/C's synthetic credential domain. The harness is deterministic from a fixed reviewed seed/trace schedule; that seed is not passed to R or placed in R-readable arguments, configuration or artifacts. V remains outside R. Separate decoys detect whether a search missed a store or used a wrong path. Every source location is identified in V's manifest and has an independent presence witness before an access-denial claim can pass.

Mandatory synthetic locations: protected regular file/auth home; C initial environment; C live heap; fixture credential-store entry or deterministic store mock; C session-keyring/Secret-Service mock as applicable; private config/cache; boundary log; crash dump; opaque capability registry. Avoid planting into production locations or invoking a real credential-manager item. A mock-store pass establishes IPC policy only; qualification of a native store requires a separately authorized disposable native-store fixture and cannot be silently substituted.

P's manifest pins OS edition/build/patch or exact kernel/config/distribution, architecture, local filesystem, boot/security policy, principal/token/group/privilege or UID/capability state, namespace/LSM/sysctl/ABI details, cgroup delegation, process/desktop/session topology, B/C/T/adapter/tool versions and digests, grant/revocation profile, auth-store mode, every output/artifact/log/dump sink, launch/configuration hashes, fixture and observer versions, seed identity, case schedule and stop policy. Unknown mandatory fields block qualification. A manifest also enumerates every Recursion-readable scope, not merely the expected output directory.

R is a hostile probe under **exactly** the intended Recursion identity and sandbox, allowed to attempt the documented operations without privilege escalation outside its granted synthetic scope. V can inspect final R snapshots under independent observer privileges without granting those privileges to R. To avoid contaminating the very domain being tested, R does not receive S to perform matching; it records authorized surface reads, and V performs the secret matching outside R. R logs source IDs and return codes, not target secret values in shared reports. Failed/leaking trace bytes stay in a sealed synthetic evidence area and are represented in the result by case ID and finding class.

### Required paired contrasts

For each applicable case, run the same deterministic workload and observer coverage in two profiles: boundary disabled (synthetic same-user/insecure controls) and boundary enabled. Disabled must actually expose the intended fixture or permit the known-bad operation; it need not expose every source with every mechanism. A missing disabled leak makes that case **invalid/unknown**, not proof of safety. Enabled must preserve an allowed, useful nonsecret task result; denying every request is a rejection/unsupported result, not a usable boundary pass.

Additionally run enabled with S0 and S1 while keeping public inputs, deterministic scheduler choices and fake provider result equal. Compare approved observable transcripts for equality except preregistered public randomness/IDs, lengths and timing normalizations. This is a bounded relational test for dependence on secrets. It does not eliminate all side channels or excuse unexpected secret-dependent fields. Never normalize a newly discovered difference after seeing results merely to obtain PASS.

### Surface coverage

V's evidence inventory covers all R-readable filesystem roots, home/config/temp trees, alternate streams/xattrs as supported, mount aliases, registry, process command lines and environments, accessible process/mapping memory, snapshots/core/minidumps, inherited handles/FDs, pipes/sockets/shared memory, normal/debug/audit/error logs, telemetry queues, transcripts/context/compaction caches, tool outputs, stderr/stdout/PTY/ConPTY, artifact staging/exports, filenames/metadata, crash/recovery spools and update/diagnostic bundles. Secret-store response and authentication-helper channels are explicit entries. Desktop/clipboard capture is either tested safely with synthetic values or proven outside R's permitted domain; it cannot be omitted because the nominal workflow is headless.

Observation occurs before launch, after fixture load, at control/tool/output barriers, before and after failure/restart, and after settlement. Per-boundary taps capture **before data enters R**, since redaction after receipt already violates “never holds.” R memory snapshots supplement continuous channel evidence; snapshots alone cannot exclude a transient copy between samples. Surfaces not enumerable/observable must be listed as unresolved coverage and prevent a universal surface-coverage claim. Reachable helper endpoints and authority mutation paths belong to the inventory even if no file is readable initially.

### Result oracle and stop conditions

A case is **PASS for its bounded predicate** only if its mandatory manifest fields are known, S presence and fault injection witnessed, insecure/positive detector controls succeed, every required surface is observed, enabled direct/induced access is denied where required, no forbidden material is detected, allowed nonsecret work completes, no external egress occurs, and an independent reviewer accepts the trace. This is not a global security guarantee.

**FAIL:** any credential transfer into R, prohibited effective access, unsafe capability, authority widening, unfenced effect/restart, misleading settlement, or silent downgrade. **UNKNOWN/BLOCKED:** unavailable mechanism/target, incomplete source/sink coverage, lost observer, unconfirmed fault, unreproducible schedule, unresolved store behavior, or missing useful compatibility. **UNSUPPORTED:** the profile cannot enforce a required invariant without changing the granted workflow. “No data,” zero cases and inability to start are never zero failures.

Abort before any real-secret location, account credential, external address or unapproved privilege/configuration change is touched. Stop the affected run on first confirmed synthetic leak/escape, preserve sealed evidence, revoke its synthetic grants and do not retry automatically under weaker isolation. On stalled drain or observer loss, follow the preregistered safe stop and report unknown. No test authorizes destructive host resets, permanent changes or real credential revocation; those need separate scope.

The competing designs below are original architectural inferences, each subject to the same accepted floors, threat model and unexecuted qualification gates. Negative controls test rejection sensitivity and cannot win the comparison.

### Explicit non-results and next decision-ready evidence

No boundary was implemented or exercised; no provider, account, model, credential, live host or target test was called; no language/store/framework/sandbox/runtime/vendor was selected; no accepted decision or repository file was changed. Source-document support is not a zero-leak measurement. Development and native qualification require separately authorized work.

The critical remaining questions are exact C/T separation and output-release behavior for each desired CLI, operator-provisioning feasibility on each precise floor, complete R-readable/control closure including helpers and updates, lifecycle conformance, and independently accepted E01–E25 evidence. These are bounded unknowns with the falsifiers and handoffs above. A successful direct-read fixture alone is not enough to promote any row to strong-qualified.
